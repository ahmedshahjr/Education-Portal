# ADR-008: Long Keys, Guid Public Ids and Numeric Enums

## Status

Accepted

## Date

2026-11-11

## Context

The template gave every entity an `int Id`, and the API exposed it in routes (`/api/Schools/{schoolId:int}`), DTOs and `Created` responses. Sequential numbers let a caller guess and walk other records, which is the first step of an insecure direct object reference (IDOR) attack, and they leak how many rows exist. Enums were stored as strings with `HasConversion<string>()`, because the old engineering rule (ENG-ENTITY-10, ENG-EF-09) said so, and three of them had no explicit member values. The JSON enum converter also accepted numbers. There are no EF Core migrations yet, so changing key and column types is cheap now and expensive later.

The maintainer set the standard on 2026-11-11 for .NET 10 and EF Core 10.

## Decision

- **Keys.** `BaseEntity` has a `long Id` primary key (`bigint`) for foreign keys, joins, query filters, claims and the audit log, and a `Guid PublicId` (version 7, set at creation) mapped as an alternate key for every entity.
- **API.** DTOs, routes (`{id:guid}`), query strings, bodies and `Created` results carry only the `Guid`. Handlers resolve it to the `long` (`ResolveIdAsync`) before any business logic, through the tenant query filters.
- **Enums.** Every member has an explicit number. The API sends and accepts names only (`JsonStringEnumConverter(allowIntegerValues: false)`, `{kind:alpha}` routes, `EnumNames.TryParse`). EF Core stores the number; `HasConversion<string>()` is not allowed. Each enum column has a lookup table seeded from the enum with a foreign key, so reports can join to names and the database refuses an undefined number.
- **Rules and guards.** The [identifiers-enums skill](../../../docs/ai/engineering/identifiers-enums/SKILL.md) (ENG-ID-01..05, ENG-ENUM-01..04) holds the rules; `compliance-guard.py` blocks enum members without a number, enums stored as strings, `int` ids and `{id:int}` routes.

## Rationale

- EF Core already maps enums to numbers by default; strings cost space and break when a member is renamed, while numbers break only when renumbered, which explicit values and the guard prevent.
- An alternate key keeps joins and foreign keys on a compact `bigint` while the API gets an identifier that cannot be enumerated. Version 7 Guids are time-ordered, so the unique index grows at its end.
- Resolving the `Guid` in the handler keeps endpoints thin and puts the lookup behind the same query filters as every other read, so tenant isolation is unchanged.

## Consequences

- Positive: no internal number reaches a client; enum data cannot be corrupted by reordering members; reports can read enum names from the lookup tables.
- Negative: one extra unique index per table, and handlers that take an id do one extra lookup (or filter on `PublicId` directly).
- A `Guid` is not an access check: authorization and tenant filters still decide what a caller may see (ENG-ID-04).
- Breaking API change for the Angular client (ids are now strings); it is regenerated by NSwag and updated in the same PR.

## Alternatives Considered

- **Guid primary keys.** Simpler, but wider foreign keys and indexes on every table, and the maintainer asked for `long` keys.
- **Encoding the `long` (Hashids/Sqids) instead of storing a Guid.** No extra column, but the id is reversible by anyone with the salt and ties public ids to the key forever.
- **PostgreSQL native enum types.** Readable in SQL, but adding a value needs a migration with `ALTER TYPE` and the type is provider-specific; integer columns with lookup tables give the same readability.
