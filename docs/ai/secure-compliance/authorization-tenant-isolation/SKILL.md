# Authorization and tenant isolation (MUST follow)

Part of the mandatory secure coding and compliance rules. Also follow the [overview skill](../SKILL.md): its rules for AI assistants, exceptions process and PR checklist apply to every change. Rule IDs are stable; cite them in reviews and PRs. If a request would break a rule here, stop, name the rule ID and propose a compliant alternative.

Framework abbreviations: **800-53** = NIST SP 800-53 Rev 5 (FedRAMP 20x Class C (Moderate) and GovRAMP baselines); **SOC 2** = AICPA Trust Services Criteria; **ISO** = ISO/IEC 27001:2022 Annex A; **OWASP** = OWASP Top 10:2025.

| ID | Rule |
|---|---|
| SEC-AUTHZ-01 | Access = modules enabled for the school ∩ role rights per module (View/Create/Edit/Delete) ∩ campuses assigned to the user, plus the fixed rules in AGENTS.md section 2. Enforce it **on the server in the Application layer** (the request rules, `IRequestRules`, which read the `[Authorize]` attribute on the request type; each controller action calls them). Angular hiding is only UX. |
| SEC-AUTHZ-02 | Deny by default: every request type checked by the request rules MUST declare its module and required right. A request without an authorization declaration MUST fail a test (add an architecture test that scans for it). |
| SEC-AUTHZ-03 | Every tenant-owned entity has `SchoolId` (and `CampusId` if campus-scoped), a `TenantId` column filled by the database (SEC-AUTHZ-12) and is covered by EF Core global query filters fed by the current-user/tenant service. MUST NOT use `IgnoreQueryFilters()` except in code paths that are explicitly authorized, audited and listed in the PR (the master bypass of SEC-AUTHZ-13, or the system scope of SEC-AUTHZ-14). |
| SEC-AUTHZ-04 | `SchoolId` comes only from the host-resolved tenant, never from the request body, query string or a client header. `CampusId` may come from the route but MUST be checked against the user's assigned campuses on every request. |
| SEC-AUTHZ-05 | No mass assignment: commands are explicit DTOs; never bind request data straight onto entities. Fields like `SchoolId`, `CampusId`, `CreatedBy`, role and permission fields are never client-settable unless the use case is exactly about changing them and is authorized for it. |
| SEC-AUTHZ-06 | A record that belongs to another school or campus MUST return 404 (not 403), so IDs cannot be used to probe other tenants. A disabled module or missing right returns 403. |
| SEC-AUTHZ-07 | Least privilege: new roles start with no rights. Master-tenant (cross-school) operations are separate use cases with their own authorization and audit, never a flag on a tenant use case. |
| SEC-AUTHZ-08 | Raw SQL, Dapper, background jobs, exports, reports and caches MUST apply the same tenant and campus scoping as the query filters. Cache keys MUST include `SchoolId` (and `CampusId` where relevant). |
| SEC-AUTHZ-09 | A school-owned entity's tenant filter MUST NEVER be replaced or removed. EF Core keeps one query filter per entity type, so a second `HasQueryFilter` call (for example the soft-delete filter of `BaseSoftDeletableEntity`) silently drops the tenant filter, and another school's admin can then read or change the row. New filters MUST be combined with the existing ones (`IMutableEntityType.GetDeclaredQueryFilters()`, as `ApplicationDbContext.ApplySoftDeleteFilter` does), never added in place. A lookup by public id (`FirstOrDefault(x => x.PublicId == id)`) MUST run through the filtered query, so another school's row is not found and the answer is 404. Hand-written `Where(x => x.SchoolId == schoolId)` is not a substitute for the filter. A change to the model's filters MUST keep the tenant filter of every `SchoolId` entity, and the test that proves another school's row is refused MUST be added with it. |
| SEC-AUTHZ-09 | Every new use case gets functional tests proving: unauthenticated → 401; another school → 404; another campus → 404; disabled module → 403; missing role right → 403. (Also required by AGENTS.md.) |
| SEC-AUTHZ-10 | Unknown host → 404 and nothing served. Never fall back to a default tenant. |
| SEC-AUTHZ-11 | Server-side requests to URLs supplied by users (webhooks, imports, avatars) MUST use an allow-list of hosts and block private/link-local/metadata addresses (SSRF). |
| SEC-AUTHZ-12 | **Database-level tenant isolation (ADR-026).** Every `ITenantOwned` table has a `TenantId` column (`integer`, not null, foreign key to `schools.Tenants`, indexed with `SchoolId`), row-level security `ENABLE` and `FORCE`d, the policy `TenantIsolation` (a row is visible and writable only when its `TenantId` equals `app.tenant_id`, or when `app.tenant_bypass` is `on`) and the trigger `TenantFromSchool`. The trigger sets `TenantId` from the row's school on every insert and update and refuses a row that moves to another school, so the application cannot choose the tenant. The application connects as a role that is not a superuser and does not bypass row-level security (PostgreSQL never applies it to a superuser); a production deployment MUST do the same (SEC-CFG-04). `TenantSessionInterceptor` sets the two session settings on every physical connection open. A test proves each table has all of it (`TenantRowLevelSecurityTests`). |
| SEC-AUTHZ-13 | **Master bypass (ADR-026).** The master tenant sees every tenant only through a signed-in master session on the master domain: `TenantResolution` grants it after the session check and audits every API call under it as `MasterTenantAccess`. An anonymous request on the master domain sees its own school only. A job acts as the master on its own scope and grants the bypass there, and no endpoint may do so. A test proves the anonymous and school sessions get no bypass. |
| SEC-AUTHZ-14 | **System scope and exemptions (ADR-026).** `ITenantSystemScope` is an explicit, short bypass for work with no signed-in user that creates rows of a school the request does not belong to: the self-service registration and the development seed. It is opened around that work only and disposed with it, and every use of it is named in the PR. Every entity with a `SchoolId` that is not `ITenantOwned` must be listed in `TenantIsolationModelTests` with its reason (today: the login account `ApplicationUser` and the audit trail `ChangeAuditEntry`). A new tenant-owned entity needs a migration that applies the row-level security, trigger and backfill of ADR-026 (`TenantRowLevelSecurity` migration as the example). |

Supports: 800-53 AC-2, AC-3, AC-4, AC-5, AC-6, AC-6(9), AC-6(10), SC-4; SOC 2 CC6.1, CC6.3, C1.1; ISO 5.15, 5.18, 8.2, 8.3; OWASP A01, A06.
